# Vibe Coding 版本管理手册

> 面向「让 AI 帮你改代码」的工作方式。以本项目（AutoPlay）为例，但规矩对所有项目通用。
> 要治的是一个病：**agent 改完，开发者不知道改了什么，也不敢回退。**

## 0. 一句话原则

**每一步都留下一条看得懂的记录。**

git 就是一台时间机器：记录留下了，改错了随时能回去；没留下，就只能靠记忆和运气。

## 1. 比命令更重要的三个习惯

1. **开工前 `git status` 必须是干净的。**
   上一轮还没提交就开始下一轮，两次改动混在一起，出了事谁都说不清。
2. **一个任务 = 一个提交。**
   不是「一天一个提交」，也不是「一版一个提交」。做完一件事就存一个档。
3. **让 agent 每次收尾交「变更三件套」：**
   - 改了哪些文件（`git diff --stat` 的结果）
   - 每个文件为什么改、行为上有什么变化
   - 它自己不确定、需要你拍板的点

## 2. 最小命令集（日常就这十几条）

| 命令 | 干什么 | 什么时候用 |
| --- | --- | --- |
| `git status` | 现在有哪些文件动了 | 每次开工前、提交前 |
| `git diff` | 具体改了哪几行 | 审 agent 的改动 |
| `git diff --stat` | 只列改了哪些文件、各改了多少行 | 快速扫一眼 |
| `git diff -- 文件路径` | 只看某个文件 | 挑重点看 |
| `git add 文件1 文件2` | 把文件放进「这次要提交」的篮子里 | 提交前 |
| `git add -A` | 全部放进篮子（**慎用**，容易带进垃圾） | 确认过 status 再用 |
| `git commit -m "说明"` | 存一个存档点 | 一个任务做完 |
| `git log --oneline` | 看历史 | 想知道发生过什么 |
| `git log --oneline --graph --all` | 带分支图的历史 | 分支多了以后 |
| `git show 提交号` | 看某个提交具体改了啥 | 翻旧账 |
| `git blame 文件` | 某一行是哪次提交、谁改的 | 定位「这行什么时候变这样的」 |
| `git log -S "某个字符串"` | 搜「哪次提交引入 / 删掉了这段代码」 | 找功能的来龙去脉 |
| `git restore 文件` | 撤销这个文件**还没提交**的改动（⚠ 改动直接没了） | agent 改坏了某个文件 |
| `git revert 提交号` | 撤销某个提交，并生成一个新提交 | 已经提交了要回退（安全） |
| `git reset --hard 提交号` | 硬回到某个提交，之后的改动全丢（⚠⚠ 最危险） | 只在确定不要之后用 |
| `git stash` / `git stash pop` | 把手上的改动先收起来 / 再拿出来 | 临时切去改别的东西 |
| `git tag v1.0.3` | 给当前提交盖个「版本章」 | 发版时 |
| `git branch` / `git switch -c 名字` | 看分支 / 新建并切到分支 | 大改造前 |
| `git push` | 推到远端（GitHub） | 备份 / 分享 |

> 你这台机器的 git 是 2.47，`git switch` / `git restore` 都能用。老教程里的 `git checkout` 是一回事
> （`git checkout -- 文件` 就是 `git restore 文件`）。

## 3. 一次完整的日常循环（照着做就行）

```text
1) git status                    # 确认干净；不干净先问 agent「这些改动是什么」
2) 让 agent 干活
3) git diff --stat               # 扫一眼：动了哪些文件、量级对不对
4) git diff -- 关键文件           # 认真看核心逻辑
5) 跑一下（程序能启动吗？打包过吗？）
6) git add 这次该提交的文件
   git commit -m "……"
7) git log --oneline -3          # 确认存档点长什么样
```

第 3 步的经验值：如果 agent 说「只改了个小功能」，但 `--stat` 里躺着 15 个文件、删了 800 行，
那它多半顺手重构了 —— 这时候要看明白再提交。

## 4. 提交信息怎么写

一句话原则：**让三个月后的你看懂。**

推荐格式：

```text
<一句话：做了什么>

为什么：……
影响：哪些文件 / 行为变化 / 要不要重新打包 / 要不要传曲库 json
```

真实例子（本项目）：

```text
增量更新：客户端 update.py / 更新器 updater.py / 发版端 make_update.py + 设计文档；
打包端加「小 exe 复用戳」减少假变化

影响：发版要跑 make_update.py；老版本（<1.0.2）没有更新器，只能走完整包
```

反例（等于没写）：

```text
update        ← 改了啥？
fix bug       ← 哪个 bug？
优化代码       ← 优化了哪里、为什么？agent 最容易写这种
```

> 小技巧：让 agent 写提交信息时，明确要求「写清做了什么、为什么、影响什么」，不要它自己发挥。

## 5. 审阅 agent 的改动（这一节最重要）

### 5.1 三次扫描法

1. **先看规模**：`git diff --stat`
   - 文件数、增删行数跟预期对不对得上？
   - 有没有冒出你根本不认识的目录（构建产物、缓存、备份）？
2. **再看内容**：`git diff -- 主文件`
   - 关注「它顺手改了什么」：删日志、改默认值、动无关函数。
3. **最后看危险面**：
   - 有没有把密钥 / 令牌 / 口令写进代码？（本项目 `*_token_local.py`、`relay_key_local.py`
     都在 `.gitignore` 里，不该出现在 `git status` 中）
   - 有没有大文件混进来？（安装包 200MB+、差分包、zip）

### 5.2 常用的「翻旧账」命令

```text
git log --oneline -- 某个文件      # 这个文件都经历了什么
git log -S "覆盖浮窗"              # 这段字是哪次提交加进去的
git blame main.py                 # 某一行最后是谁改的
git show 5ddc999 --stat           # 某个提交改了哪些文件
git show 5ddc999 -- main.py       # 某个提交对 main.py 做了什么
```

### 5.3 追查到「哪一版引入的」

程序出问题、又不知道哪版改坏的：

```text
git log --oneline     # 找出可疑的提交范围
git tag               # 看看有没有对应的版本章
git revert <提交>      # 撤销它（生成新提交，历史保留）
```

## 6. 分支和标签：什么时候用

- **master / main 永远保持「能跑」。** 用户拿到的、能打包装机的版本，都在主力分支上。
- **大改造开分支。** 比如「重做整个编辑器」，就 `git switch -c 编辑器重做`，
  改崩了直接切回来，不影响主力。
- **发版一定打 tag。** tag 是永久路标：

```text
git tag v1.0.3                          # 轻量标签
git tag -a v1.0.3 -m "增量更新正式发版"    # 带说明（推荐）
```

本项目要保证**三样东西对得上**：

```text
git tag v1.0.3  ←→  发布\AutoPlay * 安装程序 v1.0.3.exe  ←→  更新包\manifests\1.0.3-*.json
```

以后「用户说 1.0.3 有问题」，你能立刻切到那个提交、重新打出同一版来复现。

> 注意：仓库里现在有 v0.2 ~ v1.15.2 一堆旧标签（老版本号体系），和现在的 v1.0.x 不是一回事。
> **新版本号就用 v1.0.3 这种**，别再混着用了。

## 7. 出事了怎么办（决策表）

| 我想要 | 命令 | 危险度 |
| --- | --- | --- |
| 撤销某个文件**没提交**的改动 | `git restore 文件` | ⚠ 改动直接消失 |
| 撤销**全部没提交**的改动 | `git restore .` | ⚠⚠ 全部消失 |
| 手上有改动，但想临时切走干别的 | `git stash` … `git stash pop` | 安全 |
| 已经提交了，想撤销那次提交 | `git revert 提交号` | 安全（历史保留） |
| 提交信息写错了 | `git commit --amend -m "新的"` | 只能改**最后一次**，且没推过 |
| 还没提交，但想把文件加进忽略 | 写进 `.gitignore`，再 `git status` 确认 | 安全 |
| 想回到某个历史版本看看 | `git switch --detach v1.0.2`，看完 `git switch master` | 安全 |
| 想把当前分支硬回到某个提交 | `git reset --hard 提交号` | ⚠⚠ 之后的提交脱离分支 |

> 规矩：**`reset --hard` 之前先 `git stash` 或先 `git tag` 存个点**，这样还有救。

## 8. 用 AGENTS.md 给 agent 立规矩

项目根目录放一个 `AGENTS.md`，agent 每次开工都会读。这是「用制度代替口头交代」。

可以直接抄的一段：

```markdown
## 版本管理规矩（必须遵守）
- 一轮任务只做一件事；做完立刻给出：改动文件清单 + 每个文件为什么改 + 你不确定的点。
- 改完必须更新 CHANGELOG.md（写人话）；提交信息用「做了什么 / 为什么 / 影响」三段式。
- 不许提交：发布产物（发布/、发布中转版/、更新包/、build_*、dist_*）、
  密钥文件（*_token_local.py、relay_key_local.py）、缓存（__pycache__）。
- 不许顺手重构无关代码；确实需要动，先说清楚再动。
- 改完必须能跑：至少 import 通过 / 能启动；涉及打包的要说明怎么验证。
```

## 9. 可以直接复制给 agent 的话术

- 「开工前先 `git status`；如果有没提交的改动，先告诉我是什么，别动手。」
- 「一次只改一个功能，改完立刻告诉我该提交哪些文件、提交信息怎么写。」
- 「改完给我 `git diff --stat`，并对每个文件用一句话说明为什么改。」
- 「不要动 X 目录 / Y 文件。」
- 「写完先别提交，我要先看 diff。」
- 「这个改动能不能拆成两个提交？怎么拆？」

## 10. 本项目的发版流程（把规矩落下来）

```text
1) git status                                   # 干净
2) 改 main.py / installer.py 的 APP_VERSION
3) python -u -X utf8 build_no_relay.py           # 打「不带中转」两个包
4) python -u -X utf8 make_update.py --version X --old 上一版 …   # 清单 + 差分包
5) 更新 曲库索引\version.json / notice.json，生成 update.json
6) git add …  然后  git commit -m "发版 vX：……"
7) git tag -a vX -m "……"
8) 安装包 / 差分包传 Releases，json 传曲库仓库
```

详细口径见 `docs/增量更新设计.md`。

## 11. 常见坑

- **大文件别进 git**：安装包 200MB+、差分包、`payload*.zip`。进一次，仓库永远瘦不下来，用 `.gitignore` 挡住。
- **密钥文件永远不进 git**：写进历史就永远在，删了也没用（要当成已经泄露、去换一个）。
- **`git add -A` 之前先 `git status`**：build 目录、备份目录、`__pycache__` 都是这么进来的。
- **一次提交几百个文件 = 等于没提交**：出了问题只能整块回退。
- **中文文件名**：PowerShell 里记得加引号，`git add -- "曲库索引/README.md"`。
- **提交前自查**：`git status` 里出现 `*_token_local.py`、`*.exe`、`*.zip` 就停下来问一句「这该进吗」。

## 12. 速查表

```text
看状态            git status
看改了什么        git diff --stat
看具体改动        git diff -- 文件
存一个档          git add 文件…  然后  git commit -m "做了什么/为什么/影响"
看历史            git log --oneline
看某次提交        git show 提交号
找某段代码的来历   git log -S "字符串"
撤销没提交的改动   git restore 文件
撤销已提交的改动   git revert 提交号
临时收起改动      git stash   /   git stash pop
发版盖章          git tag -a v1.0.3 -m "说明"
大改造            git switch -c 分支名
危险操作          git reset --hard（用前先 tag 或 stash）
```

---

**最后一句**：你不需要背下所有命令。只要坚持两件事 —— **开工前 `git status`，收工后一个提交**。
做到这两条，agent 再怎么改，你都查得回来。
