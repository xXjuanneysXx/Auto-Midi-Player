# 发版策略：包数、下载量、中转次数（AutoPlay）

> 写于 2026-10-05（v1.0.7 发布之后）。
> 增量更新本身的原理 —— 哪些文件算「增量文件」、怎么核 sha256、怎么回滚 —— 在
> `docs/增量更新设计.md`。这篇只谈**策略**：每次发新版到底该做几个差分包、
> 怎么让用户少下载、又别让人一直串着升级。

## 0. 一句话结论

每个版本只出 **4 个包**：完全版 / 精简版 × {**上一版 → 新版** 的小包，
**更老的支持版本 → 新版** 的合并包}。

这不是什么新玩法，只是把现在这套「每个旧版本一份直达包」里**内容完全一样的那几份
合成一份** —— v1.0.7 实测它们本来就一模一样（见 §3.5）。

## 1. 先看现在（v1.0.7 实况）

发一次版传了 8 个差分包：

| 差分包 | 完全版 | 精简版 | 说明 |
| --- | --- | --- | --- |
| `1.0.6 → 1.0.7` | 21.45 MB | 6.49 MB | 相邻包，只有新版真正改过的东西 |
| `1.0.5 → 1.0.7` | 29.44 MB | 14.72 MB | 累积包 |
| `1.0.4 → 1.0.7` | 29.44 MB | 14.72 MB | 累积包 |
| `1.0.3 → 1.0.7` | 29.44 MB | 14.72 MB | 累积包 |

`update.json` 里每个 edition 底下挂 **8 条** `patches`：这次新做的 4 条，
加上从上一版清单**接着带过来**的 4 条老包（`1.0.3→1.0.6`、`1.0.4→1.0.6`、
`1.0.4→1.0.5`、`1.0.5→1.0.6` —— 那些早就传上去了，不重做）。

客户端怎么挑（`update.py`）：

* `patch_for()`：先找「`from` == 我现在这版」的**直达包**；同一个 `from` 挂了好几条时
  挑 `to` 最新的那条（免得先升到中间版本、还得再点一次更新）；
* 没有直达包就 `patch_chain()`：在清单里按 `from → to` 做 BFS，找一条到最新版的
  **最短链**，把链上的包**一次性下好**，交给更新器按顺序盖（任何一个对不上就整条链回滚）；
* 都接不上 → 退回完整安装包。

实测 1.0.6 / 1.0.5 / 1.0.4 / 1.0.3 四个版本都能**一跳到位**。

## 2. 比什么：四个数字

| 口径 | 含义 | 谁在意 |
| --- | --- | --- |
| 包数 | 每次发版要传几个附件 | 发版的人（上传时间、release 页面） |
| 下载量 | 用户升级要下多少 MB | 用户（尤其精简版 / 流量党） |
| 跳数 | 要盖几个包 | 用户体感 —— 现在永远是 **1 次**，见下 |
| 占用 | Gitee / GitHub Releases 累计占多少 | 仓库 |

关于「跳数」：客户端会把一条链上的包**全下完之后一次性交给更新器**，所以哪怕链上有
4 个包，用户也只点一次「立即更新」。链的代价**只在下载量上，不在操作次数上**。

## 3. 为什么包数会涨

还活着的旧版本有 N 个 → 每个版本一份直达包 × 完全版/精简版 2 份 = **2N**。
现在支持 1.0.3 起，N=4 → 8 个包。等 1.0.8、1.0.9 出来、旧版本还留在支持范围里，
就是 10 个、12 个……

「支持到多老」写在 `update.json` 的 `min_supported`（现在是 `1.0.3`）里；
低于它的版本只能下完整安装包。

## 3.5 关键实测：那几份「累积包」本来就是同一个东西

把 v1.0.7 的 `1.0.3→1.0.7`、`1.0.4→1.0.7`、`1.0.5→1.0.7` 三个包解开对比：

* 完全版：都是 **9 个文件**，路径和 sha256 **逐个相同**；
* 精简版：都是 **12 个文件**，同样逐个相同；
* 包里 `_patch\manifest.json` 只差一个字段：`from`（分别是 1.0.3 / 1.0.4 / 1.0.5），
  `files` 一模一样、`removed` 都是空。

也就是说这三份 29.44 MB 的包**内容本来就一样**，我们传了三遍（精简版同理）。
压缩后字节不同，只是因为 manifest 里那一个字符串、以及 zip 内每个文件的时间戳。

完全版这 9 个文件长这样：

```text
1.0.3 / 1.0.4 / 1.0.5 → 1.0.7（三份完全相同）
  AutoPlay.exe
  _internal\base_library.zip
  _internal\concrt140.dll                 ┐
  _internal\msvcp140.dll                  │ 1.0.6 那次补上的 VC 运行库：
  _internal\msvcp140_1.dll                │ 从 1.0.3 升上来要带，
  _internal\msvcp140_2.dll                │ 从 1.0.6 升上来不用
  _internal\msvcp140_codecvt_ids.dll      │
  _internal\vcomp140.dll                  ┘
  _internal\pay.jpg

1.0.6 → 1.0.7 只改 2 个：AutoPlay.exe、_internal\base_library.zip
```

## 4. 三条路

### 方案 A：只出相邻包（上一版 → 新版），更老的让客户端串

* 包数：**2**（永远不涨）
* 下载量：1.0.3 的用户要下
  `1.0.3→1.0.4 (21.4) + 1.0.4→1.0.5 (21.4) + 1.0.5→1.0.6 (29.4) + 1.0.6→1.0.7 (21.5)`
  ≈ **94 MB**（完全版）/ ≈ 34 MB（精简版）
* 跳数：1 次操作，但**下 4 个包**
* 结论：最省上传、最费用户流量。

### 方案 B：每个旧版本一份直达包（现在这样）

* 包数：2N，一直涨
* 下载量：一跳（21.45 / 29.44 MB）
* 结论：用户最舒服、上传最累，而且一半是**重复内容**（见 §3.5）。

### 方案 C（推荐）：相邻包 + 「同一份合并包挂多个 from」

* 包数：**4**（完全 / 精简各 2），与历史版本数量无关
* 下载量：上一版的用户 21.45 / 6.49 MB，更老的 29.44 / 14.72 MB
* 跳数：1
* 做法：把「改动文件集合完全相同」的旧版本合成一组，**只打一个 zip**；
  在 `update.json` 里给组里每个 `from` 各写一条 `patches`，
  **URL / size / sha256 都指向这同一个包**。

```text
现在的 update.json（完全版，新做的 4 条）
  1.0.3 → 1.0.7   .../AutoPlay-patch-full-1.0.3-to-1.0.7.zip   (29.44 MB)
  1.0.4 → 1.0.7   .../AutoPlay-patch-full-1.0.4-to-1.0.7.zip   (29.44 MB)  ← 内容同上
  1.0.5 → 1.0.7   .../AutoPlay-patch-full-1.0.5-to-1.0.7.zip   (29.44 MB)  ← 内容同上
  1.0.6 → 1.0.7   .../AutoPlay-patch-full-1.0.6-to-1.0.7.zip   (21.45 MB)

方案 C 的 update.json（完全版，只传 2 个包）
  1.0.3 → 1.0.7  ┐
  1.0.4 → 1.0.7  ├─ 都指向 .../AutoPlay-patch-full-1.0.3-1.0.5-to-1.0.7.zip (29.44 MB)
  1.0.5 → 1.0.7  ┘
  1.0.6 → 1.0.7     .../AutoPlay-patch-full-1.0.6-to-1.0.7.zip   (21.45 MB)
```

为什么安全（这是**等价变换**，不是新玩法）：

* 更新器只认包里的 `_patch\manifest.json`：`files`（要写哪些文件 + 每个文件的 sha256）
  和 `removed`（新版里没有了、要删的）。它**不看 `from`**，也不管你是从哪一版升上来的。
* 组里每个版本的「改动集合」完全相同，所以同一份 `files` 对组里任何一版都成立
  （多写的文件本来内容就一样，重写一遍没有任何坏处）。
* `removed` 取**组里各版本的并集** —— 更新器对「要删的文件不存在」是静默跳过，
  所以并集多列几条是安全的。
* 分组键 = 「改动文件集合的指纹」，比如 `sha256(sorted(files) + sorted(removed))`；
  指纹相同才合并。

### 方案 D（更彻底）：把程序自己的代码从 exe 里拆出来

见 §6。做到了，补丁会从 20 MB 级掉到 KB~MB 级，那时候「包数」基本无所谓了。

## 5. 再激进一点：连相邻包也并进去，只剩 2 个包

* 一份合并包覆盖**所有**支持版本：`files` = 各组并集，`removed` = 各组并集
  → 每次发版只有 **2 个包**（完全 / 精简）。
* 代价：上一版的用户也多下 8 MB
  （完全版 21.45 → 29.44、精简版 6.49 → 14.72）。
* 可以定个自动规则：发版时算一下，**合并包大小 ≤ 相邻包 × 1.3** 就合并成一份，
  否则保留小包。按 v1.0.7 的数据（29.44 / 21.45 = 1.37）就是"保留小包" →
  回到 4 个包。

## 6. 顺带说清楚：补丁为什么这么大

v1.0.7 只改了 `main.py` 一个源码文件，补丁却有 21.45 MB（完全版）。原因：

* PyInstaller 把**程序自己的模块编译进 `AutoPlay.exe` 里的 PYZ** —— 改一行
  `main.py`，整个 exe 就变了，整个 exe 进补丁（21 MB）；
* 顺带 `_internal\base_library.zip`（标准库 pyc 包）每次打包都会重新生成、字节不同。

彻底的解法（建议排期做，别急着塞进小版本）：

1. 打包时把程序自己的模块（`main.py` / `library.py` / `editor.py` …）**不塞进 exe**，
   改成放 `_internal\app\*.pyc`（或一个独立的 `app.zip`），启动时加进 `sys.path`；
2. 那样「只改 `main.py`」的补丁 ≈ `app\main.pyc`，几十 KB；
3. 要验的点：exe 正常启动、`edition` / 资源（图标、`pay.jpg`、`mp3midi` 那一套）
   还找得到、增量更新后能启动、完全版和精简版都过一遍。

## 7. 顺手要做的两件小事

1. **定期把 `min_supported` 往前推**（比如只支持最近 4~5 个版本）。它不影响包数
   （包数看「分组数」），但能缩短 `update.json` 里的 patches 列表、少带早年的老包，
   也让合并包覆盖的版本不至于越滚越老。
2. **老包不要删**：清单里「接着带过来」的那些包早就传上去了，还有人可能正在升级，
   删掉那条链就断了（客户端只能退回完整包）。release 附件留着就行。

## 8. 落地清单（要改什么）

只改发版端 `make_update.py`，客户端一行都不用改：

1. 现在：`for old in old_versions: diff(...) → build_patch(...)`。
   改成：先对每个 `old` 算出 `(changed, removed)` → 按指纹**分组** → 每组只
   `build_patch()` 一次（组名用组里最老的 `from`，例如
   `AutoPlay-patch-full-1.0.3-1.0.5-to-1.0.7.zip`）→ `update.json` 里组内每个 `from`
   各写一条，共用同一个 URL / size / sha256。
2. 包里 `_patch\manifest.json` 的 `from` 写成组里各版本的列表
   （`"1.0.3,1.0.4,1.0.5"`）—— 更新器不看它，纯粹给人看。
3. 可选开关 `--merged`：连相邻包一起并进合并包，只出 2 个包（见 §5）。
4. 发版命令**不变**：

   ```bat
   python -X utf8 make_update.py --version 1.0.8 --old 1.0.7 1.0.6 1.0.5 1.0.4 ^
       --patch-base "https://gitee.com/juanneys/midi-music/releases/download/v1.0.8" ^
       --package-base "https://github.com/xXjuanneysXx/Auto-Midi-Player/releases/download/v1.0.8" ^
       --min-supported 1.0.4
   ```

5. 验证（v1.0.7 就是这么验的）：
   * 从**真实安装包**里抽出 payload：单个 exe 的最后 17 字节是「尾巴」
     （`APAYLOAD1` + 8 字节偏移），照它把中间那个 zip 抽出来，`app\` 那棵树就是安装目录；
   * 套上差分包，再跟 `更新包\manifests\<新版本>-<edition>.json` **逐文件核 sha256**；
   * **每个 `from` 都要跑一遍**（完全版 / 精简版 × 每个旧版本），
     要求「文件数 / 内容不对 / 缺 / 多」全是 0。
   * 实测（v1.0.7）：完全版 2127 个文件、精简版 193 个文件，
     1.0.6 → 1.0.7 和 1.0.3 → 1.0.7 两条路线全对。

## 9. 决定（待拍板）

- [ ] 另外排期做「拆 exe」（方案 D，根治补丁体积）
